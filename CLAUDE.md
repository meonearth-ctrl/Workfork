# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Workforce Planner: shift scheduling, demand forecasting, time & attendance and leave management. Next.js 16 (App Router, Server Actions), React 19, TypeScript, Tailwind 4, Drizzle ORM on Postgres, Vitest.

## Next.js 16 is not the version in your training data

`AGENTS.md` (regenerated by `next dev`, keep it committed) says: APIs and conventions changed — read the guide in `node_modules/next/dist/docs/` before writing Next.js code. Things that matter here:

- `cookies()`, `headers()`, `params` and `searchParams` are async only. Page props use the generated `PageProps<"/route">` / `LayoutProps<"/route">` helpers (`npx next typegen` refreshes them).
- `middleware` is now `proxy`: see `src/proxy.ts`.
- `cacheComponents` is deliberately **off** (`next.config.ts`). Every page is per-user and dynamic; mutations call `revalidatePath()`. Don't add `"use cache"` or turn the flag on without restructuring pages around `<Suspense>`.
- `next.config.ts` keeps the `@tailwindcss/turbopack` CSS rule (there is no PostCSS config — removing it breaks Tailwind) and lists PGlite in `serverExternalPackages`.

## Database

`src/db/index.ts` picks the driver: `DATABASE_URL` set → postgres-js (pool size `DATABASE_POOL_MAX`, default 10); otherwise **PGlite**, an embedded Postgres in `./.data/pglite` (override with `PGLITE_DIR`). PGlite is single-process: stop any running `next dev`/`next start` before `db:reset` or `db:setup`, or use a different `PGLITE_DIR`.

`scripts/setup.ts` runs migrations, then only if no location exists: without `DATABASE_URL` (or with `SEED_DEMO=1`) it seeds a deterministic demo store (employees, templates, 10 weeks of demand, auto-planned shifts, clock entries, leave); with `DATABASE_URL` it creates one location and an admin from `ADMIN_EMAIL` / `ADMIN_PASSWORD` (≥12 chars), plus optional `LOCATION_NAME`, `TIMEZONE`.

Data conventions (see header of `src/db/schema.ts`):
- Shifts are a `date` string + `startMinute`/`endMinute` from that day's local midnight; overnight shifts have `endMinute > 1440`.
- Time entries are real instants (`timestamptz`); an open clock-in has `endAt = null`. Converting local date+minute to an instant goes through `zonedInstant()` in `src/lib/data/time.ts`; instant → local day through `localDate()`.
- Dates are `"YYYY-MM-DD"` strings everywhere; `src/lib/domain/dates.ts` does all date math in UTC to avoid server-timezone/DST drift.

## Architecture

Three layers, top to bottom:

1. **`src/lib/domain/`** — pure functions, no DB or Next imports, all unit-tested:
   - `rules.ts` — labour-rule checks (`checkEmployeeShifts`, `candidateErrors`): overlap, min rest, daily/weekly max, consecutive days (errors) and qualification, approved leave, over-contract. Rules come per location (`RuleConfig`).
   - `forecast.ts` — per-hour demand forecast (same weekday over N weeks, recency-weighted, damped trend clamped to ±25 %, closed dates), `staffNeeded` (volume ÷ productivity, min staff while open, zero on closed days), `plannedCoverage`, `summarizeCoverage`.
   - `autoschedule.ts` — greedy planner: repeatedly picks the template covering the most unmet need (only if ≥ `MIN_USEFUL_SHARE` = 40 % of its hours are useful), assigns the eligible person with most remaining contract hours (people over contract last), validated with `candidateErrors`; otherwise creates an open shift. The 0.4 value was tuned by simulation — re-check over/under-staffing if you change it or the templates.
   - `timeaccount.ts` — worked minutes with statutory breaks (>6 h 30 min, >9 h 45 min), daily target = contract/5 on working days up to `until` (today), balance.
   - `leave.ts` — working-day counting, yearly vacation balance (only `vacation` counts), approved-leave dates, concurrent absence.
2. **`src/lib/data/`** (`server-only`) — Drizzle queries that assemble domain inputs. `planning.ts#getWeekPlan` is the central loader for schedule/forecast/dashboard: employees, shifts for the week ±7 days (rule checks need the neighbouring weeks), leave, forecast need, coverage and violations by shift id.
3. **`src/app/`** — `login/` and the signed-in route group `(app)/` (dashboard, `schedule`, `forecast`, `time`, `leave`, `employees`, `settings`). Each module has `page.tsx` (server component) and `actions.ts` (`"use server"`); small client components only where forms need `useActionState` or local state.

Auth (`src/lib/auth/`): scrypt password hashes; session token in an HttpOnly cookie `wf_session`, only its SHA-256 stored in `sessions`. `proxy.ts` is just an optimistic cookie-presence redirect — the real checks are `requireUser()` / `requireManager()` in **every** page and Server Action, plus location scoping (`user.locationId`, admins exempt). Roles: `employee`, `manager`, `admin`; only admins change roles or delete shared data (qualifications, nationwide holidays).

Behaviour that is easy to break:
- Employees only ever see **published** shifts; new and auto-planned shifts are drafts until "Publish week".
- Non-managers see colleagues' leave as "Away" only — the leave type (e.g. sick) is shown to managers only.
- `saveShift` blocks rule errors unless the form sends `override`.
- Forms using `useActionState` must survive React's automatic form reset: actions return the submitted `values` on error (time, leave, employee forms) or the inputs are fully controlled (`schedule/shift-form.tsx`).

Charts: `src/components/coverage-chart.tsx` (planned staff columns vs needed step line, hover tooltip, table view) uses validated categorical colours `#2a78d6` / `#eb6834`; keep text in slate tones, not series colours.
